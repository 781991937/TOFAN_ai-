# تنفيذ واجهات TOFAN AI الخلفية — البنود 80–83

**التاريخ:** 2026-10-14
**الحالة:** `PARTIALLY IMPLEMENTED` لكل من البنود 80–83؛ التنفيذ البرمجي والاختبارات المحلية موجودة، لكن لم يُربط أو يُختبر مع مشروع Supabase حي ولم يُنشر.

## حدود التنفيذ

أضيفت طبقة REST داخل المستودع القائم، دون إعادة بناء التطبيق أو إنشاء كتالوج موازٍ أو تغيير Supabase Auth أو مسارات الذكاء الاصطناعي المحلي. أكاديميًا، تعيد الواجهة إسقاطًا للبيانات الموجودة في `AcademicCatalog` ونموذج `AcademicConcept`؛ ولا تنشئ بيانات مقررات أو مفاهيم جديدة. لم تُضف اعتماديات إلى `pubspec.yaml` ولم يتغير `pubspec.lock` أو إعداد التحليل.

## العقود المتاحة

جميع المسارات تحت `/v1` تتطلب `Authorization: Bearer <Supabase access token>` باستثناء `/health`.

| الطريقة والمسار | الاستخدام |
|---|---|
| `GET /health` | فحص liveness فقط، لا يثبت اتصال Supabase. |
| `GET /v1/academic/fields` | شجرة المجالات والجامعات والكليات والتخصصات من الكتالوج الحالي. |
| `GET /v1/academic/specializations` | التخصصات وسنواتها وفصولها ومعرفات مقرراتها. |
| `GET /v1/academic/concepts` و`GET /v1/academic/concepts/{id}` | فهرس المفاهيم الكانوني وحل المفهوم بالمعرف. |
| `GET /v1/academic/courses?limit=&offset=&specialization_id=&year=&semester=` | ملخصات المقررات مع ترقيم صفحات وتصفية اختيارية. الحد الافتراضي 25 والأقصى 100. |
| `GET /v1/academic/courses/{id}` | تفاصيل المقرر والوحدات والدروس والمهارات والقدرات والمشاريع والمصدر. |
| `GET /v1/academic/lessons/{id}` | درس ومقرر مصدره، مع خيارات التقييم دون مفتاح الإجابة. |
| `GET /v1/students/me` | هوية الطالب التي أعادها Supabase Auth. |
| `GET/PUT /v1/students/me/profile` | قراءة/حفظ الملف الدراسي المملوك للمستخدم. |
| `GET/PUT/DELETE /v1/students/me/learning-state` | قراءة/حفظ/مسح حالة التعلم الخاصة بالمستخدم. |
| `GET/POST /v1/learning/assessments/{id}/attempts` | سجل محاولات المالك أو إرسال إجابات للتصحيح في الخادم. |
| `GET /v1/projects` و`GET /v1/projects/{id}` | المشاريع الفعلية في الكتالوج وربطها بمقرراتها. |
| `GET/PUT /v1/projects/{id}/progress` | قراءة/تحديث تقدم المشروع للطالب الحالي. |

تستخدم الاستجابات غلافًا موحدًا `{ "data": ... }`، والأخطاء `{ "error": { "code": ..., "message": ... } }`.

### تحقق التقييم

العميل يرسل معرفات الأسئلة واختياراتها فقط؛ لا يقبل المسار `score` أو `passed` أو `student_id`. تُحسب النتيجة من الأسئلة والإجابات الصحيحة في المصدر الكانوني، ثم تُحفظ محاولة غير قابلة لتعديل المستخدم. استجابات الدرس لا تتضمن `correctIndex`. توجد قيود SQL إضافية تجعل `percentage` و`passed` أعمدة مولدة في قاعدة البيانات. إعادة إرسال تقييم اجتازه الطالب تُرفض بـ`409`؛ ويمنع قيد التسلسل تكرار رقم المحاولة عند التزامن.

## الهوية، RLS والأسرار

- يتحقق الخادم من الـbearer token عبر Supabase Auth (`/auth/v1/user`) قبل المسارات المحمية. لا يستخدم أي معرّف طالب وارد في جسم الطلب.
- هوية الحفظ هي سلسلة `id` المعادة من Supabase Auth، أي نظير `auth.uid().toString()` في التطبيق. تستمر قراءات/كتابات الصفوف الشخصية باستخدام مفتاح anon مع JWT المستخدم، فتبقى سياسات RLS هي حد العزل.
- يضيف `supabase/migrations/0003_backend_api_resources.sql` جداول `student_profiles` و`assessment_attempts` و`student_project_progress` مع سياسات مالك مبنية على `(select auth.uid())::text`.
- لا توجد سياسة `INSERT` للمستخدم الموثق على `assessment_attempts`. العملية الوحيدة في المحول التي تستخدم `SUPABASE_SERVICE_ROLE_KEY` هي إدراج نتيجة التقييم المصححة من الخادم؛ المفتاح لا يدخل كود Flutter ولا يُكتب في السجل.
- يرفض API أي `capabilities[].verified=true` في payload حالة التعلم. هذه حماية لمسار API فقط؛ المستودع الحالي يتيح للمستخدم تحديث حمولة تعلمه الخاصة مباشرة تحت RLS، لذلك لا ينبغي اعتبار هذه الحمولة أو شارة منها شهادة موثوقة إلى أن تُفرض قواعد موحدة في قاعدة البيانات.
- يحدد CORS قائمة origins صريحة من `TOFAN_API_ALLOWED_ORIGINS`؛ القائمة الفارغة تمنع طلبات المتصفح ذات `Origin` غير المهيأ. تضيف الاستجابات `Cache-Control: no-store` و`X-Content-Type-Options: nosniff`، ويحد حجم جسم JSON إلى 256 KiB.

2. `flutter test --no-pub` — **113 اختبارًا ناجحًا** في مجموعة المشروع الكاملة.
3. `flutter analyze --no-pub --no-fatal-infos --no-fatal-warnings` — خرج ناجح بلا أخطاء تحليل. أبلغ المحلل عن **78 ملاحظة للمشروع (13 warning و65 info)**، ولم تظهر ملاحظات في الملفات الجديدة الخاصة بالـAPI؛ لم يُخفّض أو يُغيّر إعداد التحليل.
4. **8 تحققّات SQL ساكنة** نجحت: تمكين RLS للجداول الثلاثة، تطابق سياسة المالك مع UUID المحول إلى نص، القراءة فقط لمحاولات التقييم من دور authenticated، منح الإدراج لدور الخادم، غياب سياسة إدراج للمستخدم، وتقييد حالة تقدم المشروع. `git diff --check` ناجح.

### حدود الأدلة

اختبار Supabase أعلاه **اختبار عقد محلي ببديل HTTP، وليس اختبارًا لقاعدة بيانات Supabase حقيقية**. أثناء التنفيذ كانت `SUPABASE_URL` و`SUPABASE_ANON_KEY` و`SUPABASE_SERVICE_ROLE_KEY` غير مهيأة، ولم تكن أداة `psql` متاحة. لذلك لم يُشغّل PostgreSQL على الترحيل ولم تُختبر RLS فعليًا على مشروع Supabase. لا تُعد الاختبارات المحلية إثباتًا للتكامل الحي.

## ما لم يكتمل بعد

1. مراجعة الترحيل وتطبيقه في **بيئة staging** مصرح بها، ثم اختبار Auth وRLS فعليًا بمستخدمين مختلفين. لا تطبّق هذا الترحيل على الإنتاج ضمن هذا التغيير.
2. إعداد الأسرار في بيئة تشغيل الخادم، واختبار استدعاءات Auth/PostgREST الحقيقية، خصوصًا صلاحيات `service_role` للمحاولة.
3. توصيل `TofanApiClient` بمزودي البيانات والشاشات الحالية بعد توفير عنوان API، والتحقق من سلوك التدهور إلى المسار المحلي عند غياب عنوان/خدمة API. لم تُغيّر الشاشات أو السلوك الحالي في هذه المرحلة.
4. قبل الإنتاج: إضافة تحديد معدل الطلبات، ومراقبة/سجلات تشغيل منقحة من الأسرار، وفحص حمل، وإعداد CORS وHTTPS والاستضافة وإجراءات تدوير الأسرار.

## التشغيل محليًا بعد إعداد بيئة غير إنتاجية

لا تحفظ القيم في المستودع أو في تطبيق Flutter. أمثلة المتغيرات التالية أسماء/مواضع فقط:

```bash
export SUPABASE_URL='https://<project>.supabase.co'
export SUPABASE_ANON_KEY='<anon-key>'
export SUPABASE_SERVICE_ROLE_KEY='<server-only-secret>'
export TOFAN_API_HOST='127.0.0.1'
export TOFAN_API_PORT='8080'
export TOFAN_API_ALLOWED_ORIGINS='http://localhost:3000'
dart run bin/tofan_api_server.dart
```

عميل Flutter `lib/data/api/tofan_api_client.dart` يأخذ `baseUri` ودالة token provider؛ ينبغي للدالة قراءة جلسة Supabase الحالية عند كل طلب، مثل `Supabase.instance.client.auth.currentSession?.accessToken`، وألا تحفظ التوكن أو مفتاح الخدمة.
