# بوابة خط أساس خارطة الطريق

هذه البوابة هي التنفيذ الأول للمهمة **P0-1**. وهي لا تنشئ خارطة طريق ثانية، بل تضيف سجلًا آليًا يربط مصفوفة `ROADMAP.md` التنفيذية بالأدلة التي ستُجمع أثناء التطوير.

## الملفات

- `docs/roadmap_baseline.json`: سجل واحد لكل بند من البنود `01–120`.
- `tool/verify_roadmap_baseline.py`: مدقق بلا اعتماديات خارجية يطابق السجل مع `docs/ROADMAP.md`.
- `.github/workflows/flutter-quality.yml`: يشغل البوابة في كل Push وPull Request.

## نموذج الحالة

لكل بند تُحفظ الحقول التالية:

- `reference_status`: الحالة المرجعية كما وردت في `ROADMAP.md`، ولا تُعامل كدليل تنفيذ.
- `verification`: حالة التحقق الفعلية:
  - `NEEDS_VERIFICATION`: لا توجد أدلة كافية بعد.
  - `PARTIALLY_VERIFIED`: توجد أدلة لبعض النطاق فقط.
  - `VERIFIED`: توجد أدلة كود واختبار وتشغيل كافية للنطاق المسجل.
  - `BLOCKED`: التحقق متوقف بسبب بيئة أو صلاحية أو قرار خارجي موثق.
- `code_paths`: مسارات الكود ذات الصلة.
- `test_paths`: الاختبارات ذات الصلة.
- `evidence`: أدلة التشغيل أو التوثيق أو التكامل.
- `notes`: حدود الحكم والفجوات المعروفة.

السجل الأولي يضع البنود المئة والعشرين في `NEEDS_VERIFICATION` مع مرجع خارطة الطريق فقط. هذا مقصود: وجود بند في الخارطة أو وجود ملف في المستودع لا يثبت اكتماله.

## تشغيل محلي

من جذر المستودع:

```bash
python3 tool/verify_roadmap_baseline.py
```

النجاح يعني أن:

1. مصفوفة `ROADMAP.md` تحتوي بالضبط على البنود `01–120`.
2. كل بند له سجل واحد، ولا توجد سجلات زائدة أو ناقصة.
3. الاسم والمرحلة والحالة والاعتماديات متزامنة مع الخارطة.
4. كل مسار دليل مسجل موجود داخل المستودع.
5. لا يمكن ترقية بند إلى `VERIFIED` دون مسار كود ومسار اختبار.

## طريقة تحديث السجل

عند تنفيذ مهمة لاحقة:

1. أضف مسارات الكود والاختبارات الفعلية إلى البند المناسب.
2. أضف نتيجة تشغيل مؤرخة ومرتبطة بالـcommit إلى `evidence`.
3. ميّز بين دليل الوحدة ودليل التكامل ودليل staging/production.
4. رقِّ `verification` فقط عندما يغطي الدليل النطاق المذكور في البند.
5. شغّل المدقق محليًا ثم اترك CI يعيد تشغيله.

لا يغيّر المدقق حالات `ROADMAP.md` تلقائيًا، ولا يسمح بتحويل `COMPLETED/BASE` إلى اكتمال إنتاجي بالاستنتاج.
